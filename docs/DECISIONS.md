## 2026-08-03 · build environment: linux container, node 22, bundled chromium

- **decision:** development and verification happen in a headless linux container (node 22.22.2, pnpm 10, chromium 141 at `/opt/pw-browsers/chromium`). the runtime targets node >= 20 as specified; node 22 is what executes here. chromium launches in tests use `--headless=new`, `--no-sandbox` (process runs as uid 0), and `--disable-dev-shm-usage`, and tests point discovery at the bundled chromium via the `MORTAL_BROWSER_PATH` env override.
- **reason:** the spec targets macos first with system chrome; neither macos nor a display server exists in this environment. headless-new chromium is a real chromium (same profile/network/storage stacks), so isolation and lifecycle behavior verified here is real, but macos-specific paths and windowed behavior (window title, theme color, visible countdown) are **untested here** and flagged as such. windows paths/process handling are written but untested, as the spec allows.
- **alternatives rejected:** skipping real-browser verification entirely (would violate the honesty rules); bundling a separate chromium download (unnecessary, one is present).

## 2026-08-03 · at-rest encryption of notes/ai content deferred to mvp

- **decision:** `notes.body_md` and `ai_messages.content` are stored unencrypted in sqlite for the poc.
- **reason:** the poc spec explicitly allows this simplification. mvp will add at-rest encryption with key custody in the os keychain (macos keychain / windows credential manager / linux secret service).
- **alternatives rejected:** ad-hoc passphrase encryption now (would ship a fake control with no real key custody story, violating the honesty rules).

## 2026-08-03 · manager/tests transport: loopback http rpc with an admin bearer token

- **decision:** the runtime exposes one typed rpc surface (`POST /v1/rpc`) on `127.0.0.1` with a random port and an admin bearer token, defined in `@mortal/schema`. the tauri shell will broker this to the manager ui via a thin `runtime_call` command (spawning the runtime as a sidecar and passing it the endpoint + token); in browser dev mode the vite server proxies to the same endpoint. the companion's identity-scoped `/v1/self/*` surface (day 3) is separate and uses per-identity tokens.
- **reason:** one api implementation serves the manager, tests, and future sdk identically, and it is exercisable headlessly in ci. implementing a parallel pure-tauri-ipc contract would duplicate the api surface without adding enforcement.
- **alternatives rejected:** direct tauri ipc as the only manager transport (untestable without a display and a rust build), unix domain sockets (worse windows story for the poc).

## 2026-08-03 · deletion contract implemented in day-1/day-2 window, scheduler stays day 5

- **decision:** the journaled destroy contract (D0–D7) is implemented alongside the store rather than as a day-5 rewrite of a temporary "rows-only" destroy. on day 1 the filesystem steps (D2–D4) are naturally no-ops because nothing is provisioned yet; once the day-2 launcher exists they operate on real profile/files directories with no code change. the lifecycle scheduler (tick, catch-up, grace) remains day-5 scope and is not built yet.
- **reason:** a throwaway rows-only destroy would be replaced within 24 hours; the contract's halt/remove primitives are also exactly what suspend/teardown needs on day 2. every step is idempotent, so running the full contract against an unprovisioned identity is correct, not speculative.
- **alternatives rejected:** shipping a temporary destroy and rewriting it (churn, and two deletion behaviors to document honestly).

## 2026-08-03 · companion token scheme: per-identity hmac, no schema change

- **decision:** per-identity companion bearer tokens are derived as `base64url(hmac-sha256(secret, identityId))` where the secret is generated once per runtime install and stored in the `settings` table. verification is recomputation; the plaintext token is written only into the stamped companion instance config (day 3).
- **reason:** the spec's sqlite schema (migration 0001) has no token table, and adding one would deviate from the specified schema. hmac derivation gives stable per-identity tokens, strict token→identity mapping, and no plaintext token storage in the db.
- **alternatives rejected:** a new tokens table (schema deviation), storing plaintext tokens in `settings` (worse at-rest posture).

## 2026-08-03 · react versions: manager pinned to react 18, web will use next 15 defaults

- **decision:** the manager app uses react 18 as the spec pins; `apps/web` (day 7 scope, not yet built) will use next.js 15 with its default react 19.
- **reason:** the spec pins react 18 for the manager only. pnpm workspaces isolate the two react majors cleanly.
- **alternatives rejected:** forcing one react version across both apps (no benefit, fights framework defaults).

## 2026-08-03 · migration 0001 follows the poc prompt's schema block, plus indexes

- **decision:** migration 0001 implements the poc prompt's sql verbatim, adding only `idx_identities_state` (present in the foundation document's richer variant) and per-child-table identity indexes. the foundation's foreign-key references and encrypted-blob columns were not adopted.
- **reason:** the poc prompt declares itself self-contained and authoritative; where the two documents differ, it governs. the extra indexes change no semantics. at-rest encryption is separately deferred (earlier entry).
- **alternatives rejected:** foundation-variant schema with fks (deviates from the governing spec; d5 deletes children explicitly so cascade semantics add nothing in the poc).

## 2026-08-03 · companion origin policy: pin when an Origin header exists, allow token-only otherwise

- **decision:** /v1/self requests carrying an `Origin` header must present exactly the identity's stamped companion origin, computed as chromium's unpacked-extension id (sha256 of the instance realpath, a-p alphabet) — verified against a real chromium in the day-3 smoke test. requests without an `Origin` header are allowed with a valid token.
- **reason:** the attack this defends is a malicious web page probing 127.0.0.1 — browsers always attach an Origin to those requests, so they are refused even with a stolen token. processes on the machine that can omit Origin are already inside the local trust boundary (they can read the stamped config from disk). pinning per identity also refuses one companion instance replaying against another identity's token.
- **alternatives rejected:** requiring Origin on every request (breaks curl/tests/local tools for no security gain), tofu-binding the first seen origin (weaker than computing it).

## 2026-08-03 · companion bundle carries no workspace dependencies

- **decision:** the companion duplicates the 12-line countdown formatter instead of importing @mortal/schema; a unit test pins both implementations to identical vectors.
- **reason:** the stamped template ships into every identity's browser; keeping it dependency-free keeps the surface auditable and the build trivial. zod and the schema package have no business inside an extension bundle.
- **alternatives rejected:** bundling @mortal/schema into the extension (drags zod into a mv3 worker for one function).

## 2026-08-03 · extension-id divergence on macos: canonical root at startup + origin pinned to the observed id

- **decision:** two changes after the macos smoke failure (expected `kjlb…`, chromium assigned `nkei…`). first, the runtime root is canonicalized with `fs.realpathSync` once at startup, so every derived path (profiles, files, companion instances, the `--load-extension` argument, and the id computation) starts from the same canonical form — on macos, tmp and user paths resolve through symlinks (`/tmp` → `/private/tmp`, plus firmlinks) and chromium canonicalizes extension paths before sha-256 hashing them into ids. second, prediction is no longer load-bearing: after each launch the launcher reads the browser's own target list and records the extension id chromium *actually* assigned (cached in memory and in `companion-instances/<id>/observed-extension-id`); the /v1/self origin check accepts the observed id first and falls back to the computed id only for the brief window before the first observation lands.
- **reason:** the computed id matched real chromium on linux, but macos showed that node's `realpathSync` and chromium's canonicalization can disagree. an origin check must pin to ground truth, not to a prediction of it. the divergence class is reproduced on linux by handing the runtime a symlinked root (`test/companion.symlink-root.smoke.test.ts`), which fails without the canonical-root fix and passes with it.
- **verification, honestly:** green on linux including the symlinked-root repro (canonical root, computed id == chromium-observed id, genuine origin 200 / foreign origin 403). **macos itself cannot be run in this build container** — the reporter needs to re-run `companion.smoke.test.ts` there; with observation-pinning, the origin check is correct on macos even if the computed id still diverges, and a residual mismatch now logs a warning instead of breaking auth.
- **alternatives rejected:** trusting the computed id alone (proven wrong on macos), tofu-binding the first origin seen (weaker: any origin could claim the slot), querying cdp inside the request path (latency and coupling).

## 2026-08-03 · macos constant-id failure explained: chrome component extension, not a manifest key and not symlinks

- **verified facts, in order.** (1) the companion template has no `"key"` field anywhere — pasted and grepped across `manifest.template.json`, the built `dist/manifest.json`, `build.mjs`, and the stamping code; stamped copies carry byte-identical manifests, so the constant id cannot come from our extension. (2) the constant id the mac observed, `nkeimhog…`, is `nkeimhogjdpnpccoofpliimaahmaaome` — google chrome's built-in hangouts **component extension**, shipped in branded chrome's read-only install directory with a key-derived id that is identical for every user, path, and run (see brave's pr disabling it, brave-core#24583, and simon willison's hangout_services/thunk.js writeup). (3) the bundled playwright chromium used for linux verification exposes **zero** `chrome-extension://` targets when launched bare — verified empirically in this container — which is why linux could never see this failure mode.
- **the explanation.** on the mac, branded chrome (≥137 removed `--load-extension`; the machine runs 141) did not load the stamped companion at all. the only extension target in `/json/list` was the constant hangouts component. the launcher's observation logic pinned "the only id present", and both id tests compared per-identity computed hashes against a constant component id. linux passed because its chromium both honors `--load-extension` and ships no components. the earlier symlink hypothesis was wrong; the symlinked-root canonicalization fix from the prior entry remains as defense-in-depth but was not the cause. **residual assumption, stated:** that the mac run used branded chrome — confirm via `runtime.status` (`kind: "chrome"` plus the r3 warning); a re-run with `MORTAL_BROWSER_PATH` at chromium/brave should load the companion and go green.
- **decision.** the model stays key-less with path-derived per-identity extension ids: a manifest `key` would give every stamped copy one shared id and destroy per-identity origin distinction, which is the reason the origin check exists. observation is now companion-shaped: `pickCompanionExtensionId` only considers targets whose url is exactly `chrome-extension://<id>/background.js` (component extensions expose other paths), prefers the computed id, accepts a single companion-shaped candidate under canonicalization divergence, and refuses to guess otherwise. when no companion-shaped target appears within the observation window, the runtime pushes an explicit warning ("companion did not load … branded chrome ignores --load-extension since 137; use chromium or brave") instead of silently mispinning.
- **threat-model statement (carries into docs/threat-model.md on day 7).** on platforms where the companion cannot load, the `/v1/self` surface has no legitimate browser client: origin-bearing requests are refused unless they match the per-identity companion origin, and authentication for local token-only clients rests on the bearer token alone, inside the local trust boundary. the origin check distinguishes identities exactly where a companion actually runs; it never falls back to a shared id.
- **alternatives rejected:** adding a manifest `key` (collapses all identities to one origin), keeping "single observed id wins" (proven to pin a google component), denylist of known component ids (unmaintainable; shape-based filtering is structural).

## 2026-08-03 · store distribution requires a pairing handshake: designed now, deliberately not built

- **decision:** the chrome-web-store path for the companion is designed and recorded (docs/threat-model.md, "companion trust and distribution") without any store submission or implementation in the poc. key points, fixed now so the store path cannot be built naively later: a store extension has one constant key-derived id, so the origin check degrades from "which identity" to "a genuine companion"; identity binding therefore moves into a pairing handshake — preferred: native-messaging attestation (the runtime's native host identifies the calling browser profile via its parent process's --user-data-dir and delivers {identityId, token} into that profile's companion storage); fallback: a 60s single-use pairing code shown in the manager and entered in the side panel. the hmac token remains sole authority; per-profile extension storage carries the per-identity separation; revocation is secret rotation.
- **reason:** branded chrome ≥137 killed `--load-extension` (verified on macos), so store distribution is the eventual chrome answer, and its central constraint — constant id ⇒ origin cannot distinguish identities — must shape the design before any code exists. writing it down now prevents a future "just ship the store build" from silently weakening the origin check.
- **alternatives rejected:** adding a manifest `key` to unpacked instances to converge ids early (destroys the working per-identity origin distinction on chromium/brave for zero gain today); seeding extension storage from the profile before first launch (fragile, version-dependent, not a contract chrome offers); submitting to the store during the poc (out of scope, and the handshake is unbuilt).

## 2026-08-03 · brave interstitial on a companion page load: no scripted opens, panel behavior declared natively

- **investigated, not guessed.** code audit: the companion contains zero page-navigation primitives — no tabs.create, window.open, options page, popup, or links; the only open call was `chrome.sidePanel.open` on toolbar click. empirical check on real chromium: after launch and settle, the only `chrome-extension://` target is the background service worker; **zero page-type targets** exist, so the companion opens nothing on install or startup. the brave "blocked by brave" interstitial therefore stems from the one scriptable surface: brave's sidebar implementation can surface a scripted panel open as a chrome-extension:// page-style load, and brave interposes its interstitial on page loads from sideloaded (non-store) extensions. the side panel itself working (as reported) is consistent with a one-off page-style open, not a broken panel.
- **decision:** the companion now performs no scripted navigation at all. panel opening is declared as native browser behavior via `chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true })`; a guarded `sidePanel.open` remains only for engines without setPanelBehavior; there is deliberately no tab fallback — the companion never opens a page, period. a regression guard in the companion smoke asserts no page-type chrome-extension target ever exists.
- **brave note for the store-mode design (extends the pairing-handshake entry):** brave treats sideloaded-extension pages with more suspicion than chrome does, and disables chrome's built-in component extensions (which is why it was the clean macos verification target). the store-distribution design must keep the companion panel-and-worker only — any flow that requires opening a full `chrome-extension://` page (onboarding, pairing screens) risks brave's interstitial for sideloaded installs and shields friction generally. the pairing-code fallback therefore lives in the side panel, never a full page; store distribution, when it happens, additionally clears the sideloaded-page class of blocks.
- **alternatives rejected:** shields-allowlisting instructions for users (support burden for something removable at the source), a tab fallback when the panel api is missing (exactly the class of load that gets interposed).

## 2026-08-05 · the ci companion failures' true root cause: turbo strict env mode was stripping the browser override from every test task

- **what the forensics showed:** the companion-missing warning's new profile-preferences dump listed component extensions under `/opt/google/chrome/resources/…` — the failing suites had been launching the runner's branded google chrome all along, not the chromium the ci step installed and exported. `turbo run test` runs tasks in turbo 2's default strict env mode, which strips undeclared variables: `MORTAL_BROWSER_PATH` and `MORTAL_HEADLESS` were declared nowhere in turbo.json, so inside the suites the runtime's discovery fell back to chrome-first. locally the strip was invisible because the test helpers re-set the variable in-process from the dev container's `/opt/pw-browsers/chromium`; the runner has no such path. this also explains the split verdicts: the clean-clone job and both cli smokes run outside turbo (env intact, chromium, green) while every turbo test task got chrome (silent --load-extension ignore ≥141, red).
- **decision:** turbo.json declares `globalPassThroughEnv: ["MORTAL_*", "LIMINAL_*"]` and the test task hashes `MORTAL_BROWSER_PATH`/`MORTAL_HEADLESS` via `env` (a different browser must bust the test cache). the launcher now logs one line at init — kind, version, source, path of the browser identities will get — so an env var silently failing to arrive is visible in the first screen of any log instead of costing another day of archaeology.
- **kept from the archaeology, on their own merits:** playwright's chromium (chrome-for-testing 151) as the pinned ci browser with deps/userns/boot-proof; the mortal-companion.js worker rename and chooser (chromium 151's component with a generic /background.js worker is real); the 60s observation window and per-identity browser-stderr capture; the preferences forensics in the warning; the provision-time developer-mode seed and --load-extension + --disable-extensions-except pairing (chrome 138+ unpacked-extension behavior, verified harmless on 141/151). each earlier ci fix was real for the boot-proof path; none could reach suites that weren't running the installed browser.

## 2026-08-05 · phase two, enforcement upgrade #3: tool/mcp scoping per identity (schema 2.2) — GATED at the label flip

- **the boundary, stated precisely:** mortal becomes the broker for an identity's tool calls. the operator registers upstream mcp servers in `<root>/tool-servers.json`; an identity's manifest declares which of those servers/tools its agent may reach; the runtime refuses everything else. what is enforced is **the calls mortal brokers** — a connection an agent opens for itself is outside the boundary, and that is now a printed non-guarantee alongside "bring your own proxy". we do not claim to police an agent's whole world; we claim the part we actually hold.
- **enforcement lives in the runtime, not in @mortal/mcp.** the runtime is the manifest authority, so an agent that skips the mcp package and speaks the loopback rpc directly hits exactly the same refusal. putting the check in the mcp wrapper would have made it a suggestion.
- **the registry is deliberately not an api.** there is no rpc method and no agent-facing tool that registers a server: an agent able to add a server could name it into its own scope and broker anything. registration is operator-owned, on disk, outside every agent surface.
- **schema 2.2 raises exactly one ceiling,** in the shape 2.1 established for network: `permissions.tools` is representable only as `{ value: "open", enforcement: "advisory", scope: null }` or `{ value: "scoped", enforcement: "enforced", scope: <ToolScope> }`. an identity cannot claim a scope it does not have. `tools: null` on a server entry means every tool that server exposes — including ones it grows later, which is why it is the looser choice. an empty `servers: []` is legal and meaningful: a scoped identity that may reach nothing. pre-2.2 manifests upgrade on read to open/advisory, never silently to scoped.
- **the check runs before anything upstream is touched.** an out-of-scope call to a healthy tool is refused exactly as hard as one to a tool that does not exist — proven in G20 by the fact that an unregistered server is NOT_FOUND for an open identity but FORBIDDEN for a scoped one. every refusal is journaled as a `tool_refused` activity event on the identity; brokered calls journal `tool_called`. a refusal nobody can see is not evidence of anything.

## 2026-08-08 · incident: the wall came up empty behind a green healthcheck

- **the reported cause was not the cause.** the incident was called in as a root-owned /data left by pre-entrypoint boots, unreadable after the privilege drop. two things were wrong with that. first, the entrypoint had chowned /data since the tier-1 session, so the repair was already there. second, and more usefully: a root-owned volume does not produce the reported symptom. it was tested. a volume the node user cannot read at all crashes at mkdir with EACCES *before* the server listens, so there is no /health at all and the platform sees a crash loop, not `agents_live: 0`.
- **what actually produced it.** a directory left root-owned by an earlier boot is still mode 755, so the dropped-privilege process can read it. mkdir sees the directory already there and returns happily, sqlite opens the file read-only without complaint, and nothing fails until the first append — which happens inside resume, after `server.listen()` has already run. the boot promise rejects, serve.ts logs one line and sets exitCode 1, and the listening server keeps the event loop alive. the service stays UP, answers `{"ok": true, "agents_live": 0}`, and the platform's healthcheck goes green over a dead wall. reproduced exactly: a root-owned volume, an unprivileged boot, and `agents_live: 1 of 3` with SqliteError "attempt to write a readonly database" scrolling past forever.

(3) an empty boot prints a banner, not a line, because the original signal was one stderr line that scrolled away.

- **error summaries are collapsed, not truncated at the first newline.** the boot banner printed `resume error: [` in testing, because a schema validation error arrives as pretty-printed json whose first line is a bracket. a diagnostic that says "[" is the silence this incident was about.
- **verified across a simulated root-owned volume, four boots.** boot 1 as root writes the volume (3 live, all 9 paths root-owned). boot 2 unprivileged without the entrypoint now refuses at startup, naming the path and the cause, instead of limping. boot 3 through the entrypoint repairs ownership, drops, and reports `resumed: ag_yuki, ag_marlowe, ag_ash_1` with ok:true and agents_live 3. boot 4 says "already owned, nothing to repair" and resumes identically. exactly 3 spawn events exist in the record across all four boots: they were resumed, never respawned, so no birth was faked by the repair.

## 2026-08-08 · the sandbox probe stops guessing: a measured ladder, and stderr in the reason

- **two of the four suspects were refuted by reading, not by trying things.** the probe already ran before any identity spawned and before any capture started, so it was never competing with three browsers and an encoder for headroom; moving it earlier was not available because it was already first. and the container reports no missing shared libraries (the probe now checks with ldd and says so), so the sandboxed path was not short a library. the memory ceiling and /dev/shm size are now measured and reported rather than argued about.
- **the likely cause is chromium's own setuid helper, not the kernel.** debian's chromium package ships /usr/lib/chromium/chrome-sandbox and *prefers* it over the namespace sandbox. if it is not root-owned mode 4755 — some layer exporters drop the setuid bit, and a platform running containers with no-new-privileges forbids using it at all — chromium aborts outright rather than run unsandboxed. that is a browser that starts and dies on a host whose namespaces were fine all along: exactly the reported symptom, and exactly why it read as browser_crashed rather than userns_denied. two independent fixes: the image restores the setuid bit explicitly, and the probe's ladder leads with --disable-setuid-sandbox, which is not a weakening — it declines the helper so the kernel's namespace sandbox is used instead.
- **the probe is a ladder now, because which flags survive is a property of the container.** six combinations across two axes (namespace sandbox vs the setuid helper, /dev/shm vs /tmp for shared memory), ordered against the measured /dev/shm rather than a guess: a 64mb one routes shared memory to /tmp, a real one is used as chromium prefers. a userns denial or a missing binary short-circuits after one attempt, because no flag can change the kernel's answer and a boot should not spend four launches learning that.
- **the winning flags are handed to the real browsers.** the probe used to prove one hardcoded set while LiveRuntimePort launched a different one, so a passing probe was evidence about a configuration nothing else used. the identities now launch on the combination that lived.
- **chromium's stderr is the reason.** playwright reports that a target closed and throws the browser's own last words away, so the probe spawns the binary directly to capture stderr, and only then confirms the surviving flags through playwright with a real paint (shared-memory limits bite when a frame is composited, not when the browser opens). every attempt keeps its stderr; /health carries all of it alongside the container facts, and a failing boot prints the whole account rather than an adjective.
- **an early exit is a crash, not a mystery.** chromium's crash vocabulary is not fixed ("Received signal 11", a bare non-zero exit, silence), so a process we watched exit without ever announcing a debugging port is classified as crashed. only an empty message stays unknown; the first version returned "unknown" for a real segfault.
- **the gate cannot be widened by accident.** no rung of the ladder may contain --no-sandbox, and a test asserts it across every candidate: a ladder allowed to reach for that would turn a failing probe into a passing one and put external pages in an unsandboxed browser, which is the one rule tier 1 rests on.
- **verified locally, honestly bounded.** a full live boot as a dropped-privilege user with CHROME_SANDBOX=1 comes up ok:true, agents_live 3, sandbox.ok true on measured flags, with the environment block populated. the ladder was driven against stand-in binaries that reproduce each failure: a setuid-helper abort (recovered on the first rung), a shared-memory crash that only a later rung survives (walked to it, keeping stderr from all four failures), and a userns denial (short-circuited with chromium's words in the reason). what could NOT be verified here: this container's egress resets chromium's connections with and without the proxy, so a real wikipedia read still cannot happen locally — /health sandbox.ok and the first external read on the wire are the two things to check on railway after the deploy.

## 2026-08-08 · a second wall on a hetzner box (no migration, no cutover)

- **the box is a second room, not a moved one.** the stack stands up on a fresh empty database beside railway, which keeps serving production and is not touched by anything here. an empty record means the box spawns its own cast on first boot: different identities, different ids, their own clocks. that is correct for this step and would be alarming after a cutover, so the bringup doc says which line to expect (`resumed:` absent) and why.
- **the sysctl the earlier docs assumed is probably gone.** `kernel.unprivileged_userns_clone` was a debian/ubuntu patch that recent mainline kernels dropped; on ubuntu 24.04+ the knob that actually governs this is `kernel.apparmor_restrict_unprivileged_userns`. the bootstrap writes each one only if /proc exposes it, because a sysctl file naming a key the kernel does not have makes `sysctl --system` fail and takes the valid keys down with it -- the failure mode would be a box that looks configured and denies chromium its sandbox.
- **docker's apt repo may not have a 26.04 suite on day one.** download.docker.com publishes per codename and a brand-new release can lag, so the script probes for the codename's Release file, falls back to the newest suite docker does publish, and falls back again to ubuntu's own docker.io + docker-compose-v2 if the repo fails entirely. a source that 404s would otherwise break every apt update on the box from then on.
- **ufw does not filter what docker publishes.** docker writes its own iptables rules below ufw's, so a `0.0.0.0` port publish is reachable from the internet with the firewall still reporting it closed. the compose binds the showrunner to 127.0.0.1 and only caddy is public.
- **the two routes that are not ordinary json got explicit treatment, and it was verified rather than eyeballed.** the caddy config was adapted with a real caddy binary and the resulting json inspected: /events is unencoded with flush_interval -1 and no-transform, the /hls routes carry exactly one allow-origin (caddy's `header` replaces rather than appends, so it does not duplicate the wildcard the app already sets, which browsers refuse), an OPTIONS preflight on /hls is answered at the edge because the read-only api would 405 it, and the catch-all is the only encoded route.
- **the container's memory ceiling sits above the director's.** BOX_MEM_LIMIT is where the kernel starts killing; WALL_STREAM_MEM_MB is the softer line where the wall starts giving up grid frame rate, then the grid, then the hero. the first line the wall hits should never be the kernel's.
- **shm_size is 1gb.** docker's 64mb default is exactly what sends the sandbox probe walking its ladder looking for a way around; giving chromium real shared memory removes the question.
- **healthcheck start_period is 180s.** browsers, virtual screens and encoders all start before the first honest health answer, and a short period would restart-loop a boot that was going to succeed.
- **secrets are named, never committed.** infra/box/.env.example lists every variable with the secrets marked (TERRARIUM_ADMIN_TOKEN, ANTHROPIC_API_KEY) and .gitignore gained a single negation so the template is tracked while every real .env stays ignored. the doc says to generate a fresh terrarium token for the box rather than reusing railway's: two independent walls should not share a write credential.

## 2026-08-08 · docker took the user namespaces back, so the box hands them over

- **the host allowing unprivileged user namespaces is necessary and not sufficient.** the vps had `unprivileged_userns_clone=1` and `apparmor_restrict_unprivileged_userns=0` and the sandbox probe still failed with `userns_denied` from inside the container. docker re-restricts them, in two independent places: its `docker-default` apparmor profile mediates per process rather than per namespace, so it refuses the mount and pivot_root chromium performs while building its sandbox even though chromium is inside a namespace where it legitimately holds those capabilities; and its default seccomp profile allows `clone()` only when no `CLONE_NEW*` flag is set (an arg filter masking 0x7E020000, read out of moby's own profile) while answering `clone3` with ENOSYS -- and `clone(CLONE_NEWUSER|...)` is chromium's very first sandbox call.
- **the fix is `security_opt: [apparmor=unconfined, seccomp=unconfined]`, confirmed on the box.** unconfining the OUTER profile is what lets chromium build its INNER one, and the inner sandbox is the protection that actually matters here: it is what stands between a hostile page and this box, and it is far tighter than what is being given up. the container still runs unprivileged, adds no capabilities and is not privileged; what is surrendered is the runtime's syscall and mac filtering over a process that then confines itself.
- **--no-sandbox stays refused.** it is the one thing the wall will not do: external pages never render in an unsandboxed browser, and a failed probe gates external navigation off entirely rather than lowering the bar. every configuration decision here exists to avoid that flag, not to approach it.
- **a narrower seccomp profile is committed but is not what runs.** infra/box/seccomp-chromium.json is docker's own default with just the namespace syscalls ungated (seccomp filters syscalls, it does not grant capabilities: the kernel still refuses mount to a process without CAP_SYS_ADMIN, so ungating buys the container nothing on the host). it should be able to replace seccomp=unconfined and is a real tightening if it does. it is marked in its own header as untested on the box, because it is: the verified configuration is the unconfined one, and shipping an untested profile as the default would have traded a working night for a tidier diff.
- **security options are set at container creation.** a `docker compose restart` will not apply them; `--force-recreate` will. that is in the bringup doc's troubleshooting, because the failure it produces looks exactly like the fix not working.

## 2026-08-08 · why the cells were slow: measured, then fixed

- **the diagnosis came from a stopwatch, not a hunch, and the biggest cause was not in the startup path at all.** a fresh six-agent boot was instrumented at 200ms resolution (channel dir -> playlist -> stream_url in /now), each channel was joined cold with ffmpeg-as-player, one segment per profile was opened frame by frame with ffprobe, and the box's cpu was sampled with the whole room running. the numbers, before: the sixth cell's video did not exist until 60.7s after boot (channels started one per 10s tick, then each waited 4.2-4.4s for its first 4s segment); the viewer's browser then waited up to 15s more for the /now poll that carries stream_url; joins themselves were 0.07-0.09s and total cpu was 5% of four cores. so the wall was never cpu-bound and never fetch-bound: cells were slow because their streams did not exist yet, and because the client was slow to hear that they did.
- **in production the grid was not slow, it was taken dark, by a memory misread.** the pressure ladder read cgroup memory.current / usage_in_bytes, which counts the page cache. hls segment churn, sqlite and browser file io grow inactive file cache without bound, so the counter climbs forever while real memory does not: measured here, 2547mb raw against a 1281mb working set, which walked the ladder to hero_low and shut down five healthy grid channels on a box at 5% cpu. the ladder now subtracts inactive_file (both cgroup layouts), which is what docker stats reports and what the kernel reclaims before killing anything; live after the fix the same wall reads 1788mb working set where the raw counter says 2808mb, pressure none, six channels serving. this is the production bug behind cells that vanish or never appear as the box ages.
- **the first frame's floor was the gop times the stagger.** the hls muxer can only cut at keyframes, so the old 2s gop under hls_time 4 meant no playlist until ~4.4s after each encoder start, and one start per 10s tick meant the sixth encoder started at 56s. now: one keyframe per second (-g fps), 2s segments with a 1s first segment (hls_time 2, hls_init_time 1, list 10 keeps a ~20s window), and two starts per 5s tick (measured headroom makes that caution, not appetite). after: every channel's playlist lands 1.4-1.8s after its encoder starts, and the sixth cell's video exists at 23.7s instead of 60.7s. the remaining 12s is chromium+xvfb boot, which is the identities waking, not the wall lagging.
- **a profile change no longer takes the cell down with it.** a director cut used to stop the encoder behind a 3s kill grace it could never use (an x11 encoder has no stdin to close), rm -rf the segment dir, and rebuild from nothing: ~8-12s of playlist 404 per switched cell, twice per cut, into a player with no recovery path and a stable url that meant a fatal error was permanent until reload. now the encoder restarts into the same dir (the old playlist bridges the gap, epoch sequence numbers keep players riding through, stale segments swept at 120s so switches cannot fill the disk), an x11 encoder is killed immediately (sigkill is clean for hls: the playlist only ever lists completed segments), and hls.js heals: network-fatal rebuilds the player every 2s for as long as the server still advertises the url, media-fatal tries recoverMediaError first. omit_endlist keeps a stopping encoder from declaring the live stream finished.
- **the client now asks fast exactly while it is blind.** stream_url is withheld until a playlist exists (right), but the snapshot poll that carries it ran every 15s, which was most of a ready cell's remaining invisibility. the poll is a chain now: 2s while any living agent lacks a stream_url, 15s once every cell that can stream does. joins also sync two target durations from live instead of three, which with 2s segments moves a viewer from 12s behind live to ~4s and one segment less to first frame.
- **what was measured and deliberately not changed:** cpu (5% before, 7% after, of four cores; the grid stays 480x300@3 and nothing needed thinning), fetch latency (~1-2ms per playlist locally), and the hero (960x600@6 untouched; its shorter gop is faster joins at the same quality). the ffmpeg-as-player join numbers rose from ~0.08s to ~2.1s on four channels after the change, and that is the measuring stick, not the product: ffmpeg's probe window wants ~a segment of data at these tiny bitrates, while hls.js appends segments to mse without probing. six new tests pin the encoder args, the exact-key cgroup stat parse, the keep-dir restart and the sweep. 115 showrunner tests, full check green.
