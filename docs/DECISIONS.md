## 2026-08-03 · build environment: linux container, node 22, bundled chromium

- **decision:** development and verification happen in a headless linux container (node 22.22.2, pnpm 10, chromium 141 at `/opt/pw-browsers/chromium`). the runtime targets node >= 20 as specified; node 22 is what executes here. chromium launches in tests use `--headless=new`, `--no-sandbox` (process runs as uid 0), and `--disable-dev-shm-usage`, and tests point discovery at the bundled chromium via the `MORTAL_BROWSER_PATH` env override.
- **reason:** the spec targets macos first with system chrome; neither macos nor a display server exists in this environment. headless-new chromium is a real chromium (same profile/network/storage stacks), so isolation and lifecycle behavior verified here is real, but macos-specific paths and windowed behavior (window title, theme color, visible countdown) are **untested here** and flagged as such. windows paths/process handling are written but untested, as the spec allows.
- **alternatives rejected:** skipping real-browser verification entirely (would violate the honesty rules); bundling a separate chromium download (unnecessary, one is present).

## 2026-08-03 · at-rest encryption of notes/ai content deferred to mvp

- **decision:** `notes.body_md` and `ai_messages.content` are stored unencrypted in sqlite for the poc.
- **reason:** the poc spec explicitly allows this simplification. mvp will add at-rest encryption with key custody in the os keychain (macos keychain / windows credential manager / linux secret service).
- **alternatives rejected:** ad-hoc passphrase encryption now (would ship a fake control with no real key custody story, violating the honesty rules).

## 2026-08-03 · manager/tests transport: loopback http rpc with an admin bearer token

- **decision:** the runtime exposes one typed rpc surface (`POST /v1/rpc`) on `127.0.0.1` with a random port and an admin bearer token, defined in `@mortal/schema`. the tauri shell will broker this to the manager ui via a thin `runtime_call` command (spawning the runtime as a sidecar and passing it the endpoint + token); in browser dev mode the vite server proxies to the same endpoint. the companion's identity-scoped `/v1/self/*` surface (day 3) is separate and uses per-identity tokens.
- **reason:** one api implementation serves the manager, tests, and future sdk identically, and it is exercisable headlessly in ci. implementing a parallel pure-tauri-ipc contract would duplicate the api surface without adding enforcement.
- **alternatives rejected:** direct tauri ipc as the only manager transport (untestable without a display and a rust build), unix domain sockets (worse windows story for the poc).

## 2026-08-03 · deletion contract implemented in day-1/day-2 window, scheduler stays day 5

- **decision:** the journaled destroy contract (D0–D7) is implemented alongside the store rather than as a day-5 rewrite of a temporary "rows-only" destroy. on day 1 the filesystem steps (D2–D4) are naturally no-ops because nothing is provisioned yet; once the day-2 launcher exists they operate on real profile/files directories with no code change. the lifecycle scheduler (tick, catch-up, grace) remains day-5 scope and is not built yet.
- **reason:** a throwaway rows-only destroy would be replaced within 24 hours; the contract's halt/remove primitives are also exactly what suspend/teardown needs on day 2. every step is idempotent, so running the full contract against an unprovisioned identity is correct, not speculative.
- **alternatives rejected:** shipping a temporary destroy and rewriting it (churn, and two deletion behaviors to document honestly).

## 2026-08-03 · companion token scheme: per-identity hmac, no schema change

- **decision:** per-identity companion bearer tokens are derived as `base64url(hmac-sha256(secret, identityId))` where the secret is generated once per runtime install and stored in the `settings` table. verification is recomputation; the plaintext token is written only into the stamped companion instance config (day 3).
- **reason:** the spec's sqlite schema (migration 0001) has no token table, and adding one would deviate from the specified schema. hmac derivation gives stable per-identity tokens, strict token→identity mapping, and no plaintext token storage in the db.
- **alternatives rejected:** a new tokens table (schema deviation), storing plaintext tokens in `settings` (worse at-rest posture).

## 2026-08-03 · react versions: manager pinned to react 18, web will use next 15 defaults

- **decision:** the manager app uses react 18 as the spec pins; `apps/web` (day 7 scope, not yet built) will use next.js 15 with its default react 19.
- **reason:** the spec pins react 18 for the manager only. pnpm workspaces isolate the two react majors cleanly.
- **alternatives rejected:** forcing one react version across both apps (no benefit, fights framework defaults).

## 2026-08-03 · migration 0001 follows the poc prompt's schema block, plus indexes

- **decision:** migration 0001 implements the poc prompt's sql verbatim, adding only `idx_identities_state` (present in the foundation document's richer variant) and per-child-table identity indexes. the foundation's foreign-key references and encrypted-blob columns were not adopted.
- **reason:** the poc prompt declares itself self-contained and authoritative; where the two documents differ, it governs. the extra indexes change no semantics. at-rest encryption is separately deferred (earlier entry).
- **alternatives rejected:** foundation-variant schema with fks (deviates from the governing spec; d5 deletes children explicitly so cascade semantics add nothing in the poc).

## 2026-08-03 · companion origin policy: pin when an Origin header exists, allow token-only otherwise

- **decision:** /v1/self requests carrying an `Origin` header must present exactly the identity's stamped companion origin, computed as chromium's unpacked-extension id (sha256 of the instance realpath, a-p alphabet) — verified against a real chromium in the day-3 smoke test. requests without an `Origin` header are allowed with a valid token.
- **reason:** the attack this defends is a malicious web page probing 127.0.0.1 — browsers always attach an Origin to those requests, so they are refused even with a stolen token. processes on the machine that can omit Origin are already inside the local trust boundary (they can read the stamped config from disk). pinning per identity also refuses one companion instance replaying against another identity's token.
- **alternatives rejected:** requiring Origin on every request (breaks curl/tests/local tools for no security gain), tofu-binding the first seen origin (weaker than computing it).

## 2026-08-03 · companion bundle carries no workspace dependencies

- **decision:** the companion duplicates the 12-line countdown formatter instead of importing @mortal/schema; a unit test pins both implementations to identical vectors.
- **reason:** the stamped template ships into every identity's browser; keeping it dependency-free keeps the surface auditable and the build trivial. zod and the schema package have no business inside an extension bundle.
- **alternatives rejected:** bundling @mortal/schema into the extension (drags zod into a mv3 worker for one function).

## 2026-08-03 · side panel consumes sse via fetch streaming, not EventSource

- **alternatives rejected:** query-string tokens (leak surface), websockets (heavier than needed for one-way events).

## 2026-08-03 · extension-id divergence on macos: canonical root at startup + origin pinned to the observed id

- **decision:** two changes after the macos smoke failure (expected `kjlb…`, chromium assigned `nkei…`). first, the runtime root is canonicalized with `fs.realpathSync` once at startup, so every derived path (profiles, files, companion instances, the `--load-extension` argument, and the id computation) starts from the same canonical form — on macos, tmp and user paths resolve through symlinks (`/tmp` → `/private/tmp`, plus firmlinks) and chromium canonicalizes extension paths before sha-256 hashing them into ids. second, prediction is no longer load-bearing: after each launch the launcher reads the browser's own target list and records the extension id chromium *actually* assigned (cached in memory and in `companion-instances/<id>/observed-extension-id`); the /v1/self origin check accepts the observed id first and falls back to the computed id only for the brief window before the first observation lands.
- **reason:** the computed id matched real chromium on linux, but macos showed that node's `realpathSync` and chromium's canonicalization can disagree. an origin check must pin to ground truth, not to a prediction of it. the divergence class is reproduced on linux by handing the runtime a symlinked root (`test/companion.symlink-root.smoke.test.ts`), which fails without the canonical-root fix and passes with it.
- **verification, honestly:** green on linux including the symlinked-root repro (canonical root, computed id == chromium-observed id, genuine origin 200 / foreign origin 403). **macos itself cannot be run in this build container** — the reporter needs to re-run `companion.smoke.test.ts` there; with observation-pinning, the origin check is correct on macos even if the computed id still diverges, and a residual mismatch now logs a warning instead of breaking auth.
- **alternatives rejected:** trusting the computed id alone (proven wrong on macos), tofu-binding the first origin seen (weaker: any origin could claim the slot), querying cdp inside the request path (latency and coupling).

## 2026-08-03 · macos constant-id failure explained: chrome component extension, not a manifest key and not symlinks

- **verified facts, in order.** (1) the companion template has no `"key"` field anywhere — pasted and grepped across `manifest.template.json`, the built `dist/manifest.json`, `build.mjs`, and the stamping code; stamped copies carry byte-identical manifests, so the constant id cannot come from our extension. (2) the constant id the mac observed, `nkeimhog…`, is `nkeimhogjdpnpccoofpliimaahmaaome` — google chrome's built-in hangouts **component extension**, shipped in branded chrome's read-only install directory with a key-derived id that is identical for every user, path, and run (see brave's pr disabling it, brave-core#24583, and simon willison's hangout_services/thunk.js writeup). (3) the bundled playwright chromium used for linux verification exposes **zero** `chrome-extension://` targets when launched bare — verified empirically in this container — which is why linux could never see this failure mode.
- **the explanation.** on the mac, branded chrome (≥137 removed `--load-extension`; the machine runs 141) did not load the stamped companion at all. the only extension target in `/json/list` was the constant hangouts component. the launcher's observation logic pinned "the only id present", and both id tests compared per-identity computed hashes against a constant component id. linux passed because its chromium both honors `--load-extension` and ships no components. the earlier symlink hypothesis was wrong; the symlinked-root canonicalization fix from the prior entry remains as defense-in-depth but was not the cause. **residual assumption, stated:** that the mac run used branded chrome — confirm via `runtime.status` (`kind: "chrome"` plus the r3 warning); a re-run with `MORTAL_BROWSER_PATH` at chromium/brave should load the companion and go green.
- **decision.** the model stays key-less with path-derived per-identity extension ids: a manifest `key` would give every stamped copy one shared id and destroy per-identity origin distinction, which is the reason the origin check exists. observation is now companion-shaped: `pickCompanionExtensionId` only considers targets whose url is exactly `chrome-extension://<id>/background.js` (component extensions expose other paths), prefers the computed id, accepts a single companion-shaped candidate under canonicalization divergence, and refuses to guess otherwise. when no companion-shaped target appears within the observation window, the runtime pushes an explicit warning ("companion did not load … branded chrome ignores --load-extension since 137; use chromium or brave") instead of silently mispinning.
- **threat-model statement (carries into docs/threat-model.md on day 7).** on platforms where the companion cannot load, the `/v1/self` surface has no legitimate browser client: origin-bearing requests are refused unless they match the per-identity companion origin, and authentication for local token-only clients rests on the bearer token alone, inside the local trust boundary. the origin check distinguishes identities exactly where a companion actually runs; it never falls back to a shared id.
- **alternatives rejected:** adding a manifest `key` (collapses all identities to one origin), keeping "single observed id wins" (proven to pin a google component), denylist of known component ids (unmaintainable; shape-based filtering is structural).

## 2026-08-03 · store distribution requires a pairing handshake: designed now, deliberately not built

- **decision:** the chrome-web-store path for the companion is designed and recorded (docs/threat-model.md, "companion trust and distribution") without any store submission or implementation in the poc. key points, fixed now so the store path cannot be built naively later: a store extension has one constant key-derived id, so the origin check degrades from "which identity" to "a genuine companion"; identity binding therefore moves into a pairing handshake — preferred: native-messaging attestation (the runtime's native host identifies the calling browser profile via its parent process's --user-data-dir and delivers {identityId, token} into that profile's companion storage); fallback: a 60s single-use pairing code shown in the manager and entered in the side panel. the hmac token remains sole authority; per-profile extension storage carries the per-identity separation; revocation is secret rotation.
- **reason:** branded chrome ≥137 killed `--load-extension` (verified on macos), so store distribution is the eventual chrome answer, and its central constraint — constant id ⇒ origin cannot distinguish identities — must shape the design before any code exists. writing it down now prevents a future "just ship the store build" from silently weakening the origin check.
- **alternatives rejected:** adding a manifest `key` to unpacked instances to converge ids early (destroys the working per-identity origin distinction on chromium/brave for zero gain today); seeding extension storage from the profile before first launch (fragile, version-dependent, not a contract chrome offers); submitting to the store during the poc (out of scope, and the handshake is unbuilt).

## 2026-08-03 · brave interstitial on a companion page load: no scripted opens, panel behavior declared natively

- **investigated, not guessed.** code audit: the companion contains zero page-navigation primitives — no tabs.create, window.open, options page, popup, or links; the only open call was `chrome.sidePanel.open` on toolbar click. empirical check on real chromium: after launch and settle, the only `chrome-extension://` target is the background service worker; **zero page-type targets** exist, so the companion opens nothing on install or startup. the brave "blocked by brave" interstitial therefore stems from the one scriptable surface: brave's sidebar implementation can surface a scripted panel open as a chrome-extension:// page-style load, and brave interposes its interstitial on page loads from sideloaded (non-store) extensions. the side panel itself working (as reported) is consistent with a one-off page-style open, not a broken panel.
- **decision:** the companion now performs no scripted navigation at all. panel opening is declared as native browser behavior via `chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true })`; a guarded `sidePanel.open` remains only for engines without setPanelBehavior; there is deliberately no tab fallback — the companion never opens a page, period. a regression guard in the companion smoke asserts no page-type chrome-extension target ever exists.
- **brave note for the store-mode design (extends the pairing-handshake entry):** brave treats sideloaded-extension pages with more suspicion than chrome does, and disables chrome's built-in component extensions (which is why it was the clean macos verification target). the store-distribution design must keep the companion panel-and-worker only — any flow that requires opening a full `chrome-extension://` page (onboarding, pairing screens) risks brave's interstitial for sideloaded installs and shields friction generally. the pairing-code fallback therefore lives in the side panel, never a full page; store distribution, when it happens, additionally clears the sideloaded-page class of blocks.
- **alternatives rejected:** shields-allowlisting instructions for users (support burden for something removable at the source), a tab fallback when the panel api is missing (exactly the class of load that gets interposed).

## 2026-08-03 · the workspace-build rule, after the vercel failure (third instance of the class)

## 2026-08-05 · the ci companion failures' true root cause: turbo strict env mode was stripping the browser override from every test task

- **what the forensics showed:** the companion-missing warning's new profile-preferences dump listed component extensions under `/opt/google/chrome/resources/…` — the failing suites had been launching the runner's branded google chrome all along, not the chromium the ci step installed and exported. `turbo run test` runs tasks in turbo 2's default strict env mode, which strips undeclared variables: `MORTAL_BROWSER_PATH` and `MORTAL_HEADLESS` were declared nowhere in turbo.json, so inside the suites the runtime's discovery fell back to chrome-first. locally the strip was invisible because the test helpers re-set the variable in-process from the dev container's `/opt/pw-browsers/chromium`; the runner has no such path. this also explains the split verdicts: the clean-clone job and both cli smokes run outside turbo (env intact, chromium, green) while every turbo test task got chrome (silent --load-extension ignore ≥141, red).
- **decision:** turbo.json declares `globalPassThroughEnv: ["MORTAL_*", "LIMINAL_*"]` and the test task hashes `MORTAL_BROWSER_PATH`/`MORTAL_HEADLESS` via `env` (a different browser must bust the test cache). the launcher now logs one line at init — kind, version, source, path of the browser identities will get — so an env var silently failing to arrive is visible in the first screen of any log instead of costing another day of archaeology.
- **kept from the archaeology, on their own merits:** playwright's chromium (chrome-for-testing 151) as the pinned ci browser with deps/userns/boot-proof; the mortal-companion.js worker rename and chooser (chromium 151's component with a generic /background.js worker is real); the 60s observation window and per-identity browser-stderr capture; the preferences forensics in the warning; the provision-time developer-mode seed and --load-extension + --disable-extensions-except pairing (chrome 138+ unpacked-extension behavior, verified harmless on 141/151). each earlier ci fix was real for the boot-proof path; none could reach suites that weren't running the installed browser.
